# Go 服务端工作规范

## 目标与范围

- 本项目由个人维护。优先选择能直接读懂、定位和修改的实现，用明确的业务代码解决当前问题。
- 使用 Go、Gin、GORM、SQLite、zerolog；飞书使用 [官方 Go SDK](https://github.com/larksuite/oapi-sdk-go)。只支持单机单进程和 SQLite。
- 不启用 CGO。SQLite 使用纯 Go 驱动，构建、自测及发布均设置 `CGO_ENABLED=0`，不能依赖系统 SQLite 或 C 编译器。
- 保留已使用的监控、通知、Bot、Cookie 续期、Web 管理和导出能力。阶段边界及 Spec 链接见 [重构计划](docs/plan/README.md)。
- 在 `service/` 内开发。文档、面向维护者的解释和必要注释使用中文，专业术语和代码标识符可使用英语。
- 服务端文档统一放在 `docs/`：`plan/` 维护计划与阶段安排，`spec/` 维护功能需求与验收，`ticket/` 存放按需拆分的实施任务。[文档入口](docs/README.md) 维护导航，本文件保留在服务端根目录作为规范入口。
- Rust 归档只作为协议样本和行为参考；不照搬其表结构、模块树、状态机、租约或历史项目计划。

## 开始工作

1. 读取当前任务对应的 Spec，确认要交付的可观察行为和验收条件。
2. 按需查看 Spec 引用的历史协议和 fixture；若历史设计与新 Spec 冲突，采用新 Spec。
3. 直接完成本阶段的最小可用流程，包括相关管理页和错误反馈。局部实现选择自行决定，涉及功能取舍再讨论。

## 分层与依赖

| 位置 | 职责 |
| --- | --- |
| `cmd/` | 启动、配置加载和显式组装依赖 |
| `internal/handler/` | Gin 路由、参数校验、HTTP 响应；Bot 消息入口的解析和回复映射 |
| `internal/service/` | 业务流程、业务规则、事务边界和后台任务编排 |
| `internal/repository/` | GORM 模型与数据库读写；SQL 只出现在这一层 |
| `internal/infrastructure/` | 对外 HTTP Client、NGA 协议、飞书 SDK、Bark、文件资源等外部依赖的接入 |

- 调用方向为 `handler → service → repository / infrastructure`。调度器和 Bot 入口复用 service，不另写一套业务流程。
- handler 不直接访问数据库；repository 和 infrastructure 不决定通知匹配、游标推进等业务规则，也不反向依赖 service。
- `*gin.Context` 留在 handler。所有 I/O 传递 `context.Context`，数据库查询使用对应 context，外部请求设置超时。
- 优先使用具体 struct 和显式构造函数。仅在已有替换需求或真实隔离边界时定义小 interface，不为每个 struct 配套 interface。
- 数据结构优先复用；只有 API 脱敏、协议转换或业务语义不同才拆 DTO。按业务归组文件，不强制每个类型一个文件。
- 配置、日志、错误和纯内容转换可有少量共享代码；不要把业务堆进泛化的 `common`、`base` 或 `utils`。

## 调用链与日志

- 统一使用 zerolog 结构化日志，默认 `info`。HTTP 请求、Bot 事件、定时任务和启动流程各有 `trace_id`。
- 每个实际经过的 handler、service、repository、infrastructure 操作记录开始与结束，包含 `trace_id`、`span_id`、`parent_span_id`、`operation`；结束日志补充结果及耗时，根操作的父 ID 为空。
- 完整调用链指从入口经过业务层、数据库和外部请求，再到最终结果的实际调用关系。成功和失败都可串联；无需给每个 getter 或纯计算函数打日志。
- HTTP 响应携带关联 ID。异步任务建立自身的 trace 并记录来源 trace 和业务 ID，使用自己的任务 context；不要沿用已经取消的 HTTP context。
- Gin 访问日志、GORM 查询日志和外部 HTTP/SDK 请求日志接入同一套关联字段。SQL 使用占位符，记录耗时和行数；HTTP 记录方法、脱敏 URL、状态和耗时。
- 业务关键处使用 `info` 记录明确选择的参数与结果：如 watch ID、TID/UID、页码、时间范围、初始化模式、触发来源、新增数量、通知渠道 ID、续期阶段和导出数量。
- `info` 下保留上述链路和关键业务日志，不通过采样丢弃。更细的诊断信息放 `debug`；不新增独立链路采集服务。
- 凭据、Cookie、Authorization、密码、验证码、绑定码、Bark key、飞书密钥和完整收件地址必须脱敏；不要直接打印整个请求头、body、配置对象或 SQL 实参。

## 错误处理

- 错误在项目创建处，或首次进入项目代码的第三方边界，捕获 stack trace。向上返回时补充业务上下文并保留 cause，使用支持 `Unwrap` 的包装和 `errors.Is/As`。
- 所有被打印的 error，不论日志级别，都包含完整 cause 信息和非空 stack trace；栈包含函数、文件和行号。已有栈向上传递，不替换成日志函数处的栈。
- 未带栈的第三方错误在接入处补栈并注明捕获位置；panic 的恢复日志保留 panic 值和当时完整栈。不得只写 `request failed` 或单独 `err.Error()`。
- 同一个向上传播的错误在负责结束该操作的边界打印一次；下层返回错误并记录操作结果。下层若处理错误后继续执行，则在处理处记录，不静默吞错。
- 错误消息、cause 和栈的字段仍需脱敏，保留排障所需语义。HTTP/Bot 对用户返回可理解的原因和关联 ID，完整内部栈保留在日志中。
- 日志和错误辅助代码集中在一处，保持小而直接。不能仅调用 `.Stack()` 就假定普通 Go error 已有堆栈；参见 [zerolog 错误日志说明](https://github.com/rs/zerolog#error-logging-with-stacktrace)。

## 数据与后台任务

- Go 运行时的 GORM 只面向 SQLite，不保留数据库后端选择或 PostgreSQL 兼容层。按阶段增加当前用到的表和索引。
- 旧 PG 仅作为 [阶段 09 数据迁移](docs/spec/09-data-migration.md) 的只读来源；一次性迁移工具可直接读取旧库，不把 PG 依赖或旧表结构带入运行时 repository。
- 需要共同成功的帖子保存、游标/基线更新和通知记录使用本地事务；事务由 service 决定范围，repository 使用同一事务连接。网络调用不放在数据库事务中等待。
- 同一内容的重复抓取使用自然键/唯一约束去重；失败或免拉取跳过不推进未完成的游标和基线。
- 持久化时间统一使用 UTC，展示及调度按配置时区解释。SQLite 时间存储和比较使用一致格式，避免混用字符串格式进行到期判断。
- 使用进程内调度和有限并发，默认串行抓取。任务停止和异常退出需有可理解的结果，优先显式重跑；不引入分布式锁、数据库租约或通用恢复框架。
- 写入 SQLite 的凭据和通知收件地址沿用加密落盘的要求，用单个部署密钥及标准密码库实现；密钥与数据库分开保存，不搭建密钥管理平台。

## 控制复杂度

- 先交付一个可运行的业务流程，再根据已出现的重复做提取。每个新增依赖、interface 和后台组件都要能说明它解决的当前问题。
- 使用普通函数、struct、条件分支和显式依赖组装。当前范围不引入通用 Repository、Provider 注册表、命令框架、事件总线、消息队列、DI 框架、微服务或多实例协调。
- 状态字段只表达用户需要观察或业务必须判断的状态；不要按旧实现复刻审计表、worker 状态层级和跨模块清理链。
- 一次修改围绕当前 Spec。不要顺手重排无关文件、加入未来平台、预留商业化能力或生成尚未使用的代码。
- 说明协议特殊处理和业务取舍；避免复述代码的注释、机械包装函数和大段模板说明。更新行为时同步对应 Spec、API 示例和管理页。

## 验证与完成

- 不要求 TDD、覆盖率门槛、每函数单测或全量 mock。用实际运行和最少的必要检查验证当前需求。
- 解析/格式转换、游标规则、凭据写入、删除清理和已修复回归优先使用少量 fixture 或本地 SQLite 检查；简单 CRUD 和纯 UI 改动无需机械补测。
- Go 工程建立后，在 `service/` 内执行 `gofmt` 并检查差异、`CGO_ENABLED=0 go build ./...`、`CGO_ENABLED=0 go vet ./...`；存在相关测试时运行 `CGO_ENABLED=0 go test ./...`，不为满足命令空造测试。
- 联调 NGA、飞书和 Bark 按需手工执行，不作为自动检查的网络依赖；用假数据验证日志的调用关系、错误栈和脱敏。
- 文档改动检查相对链接和 `git diff --check`。报告已完成的验收、实际运行的命令及阻塞原因，不能把未运行的检查写成通过。
