# 监控目标免拉取时段设计

## 1. 目标与范围

为服务端的 TID、UID 监控目标增加按目标配置的免拉取时段。在免拉取时段内，自动运行不访问 NGA，但必须留下可审计的运行记录。免拉取结束后继续从原游标增量采集，期间累积的新内容照常保存、创建事件并通知。

本设计覆盖 Rust 服务、REST API、机器人手动运行、`/admin` 管理台、SQLite 和 PostgreSQL。`extension-standalone` 没有持久化运行记录，不在本次范围内。

领域词汇以仓库根目录的 `CONTEXT.md` 为准。“免拉取”只约束自动采集，不等同于通知静默，也不同于首次同步时的静默基线。

## 2. 行为契约

### 2.1 自动运行

启用的监控目标到期后，由统一运行协调层领取租约并确定触发来源。若自动运行命中免拉取时段，协调层必须在任何 NGA 请求之前完成以下原子操作：

1. 创建并完成一条运行记录；
2. 将记录标记为 `status = skipped`、`error_kind = no_fetch_period`；
3. 将请求页数、内容、事件、匹配和 outbox 计数全部保持为 0；
4. 不修改 TID/UID 游标，不修改 `baseline_completed`；
5. 将监控目标恢复为 `active`，释放租约；
6. 将 `next_run_at` 推进到当前连续免拉取区间的结束边界。

一个连续免拉取区间只产生一条自动跳过记录。重叠或首尾相接的规则视为同一个连续区间。免拉取跳过更新“最近完成尝试”时间，但不伪装成成功抓取。

服务在整个免拉取区间内未运行时，不补造历史跳过记录。服务恢复后处理实际已逾期的运行。

### 2.2 手动运行

管理台/API 的“立即运行”和机器人 `/watch run` 都属于手动运行。手动运行绕过免拉取时段，但不得绕过以下约束：

- 用户暂停或鉴权暂停；
- 已删除或不存在；
- 已有运行持有有效租约；
- 已有一个手动请求等待 worker 领取。

重复请求分别返回 `watch_already_running` 或 `watch_run_already_requested`，不排队多个运行。

手动运行发生在免拉取时段内时，不能消费本区间的自动跳过审计机会。若本区间尚无跳过记录，手动运行完成后应安排一次自动评估，由其写入跳过记录并推进到区间结束；若此前已经跳过，则保留原区间结束时间，不重复记录。

### 2.3 配置变更

普通配置更新不终止已领取的运行。当前运行继续使用领取时的配置快照，新配置从下一次运行生效。暂停、删除和重置继续使用各自明确的并发与租约规则。

启用且空闲的目标新增或修改免拉取配置后立即重新评估：如果当前时间已命中，创建一次免拉取跳过并更新下次运行时间。暂停目标只保存配置，重新启用后才评估，不创建暂停期间的运行记录。

## 3. 时间模型

免拉取规则使用服务配置的固定 UTC offset，与现有动态 schedule 共用日期词汇和分钟精度：

- 开始时间包含，结束时间不包含；
- 支持跨午夜，跨午夜区间归属于开始日；
- 多条规则按并集处理，不受数组顺序影响；
- 首尾相接的规则合并为连续区间；
- 全天通过 `00:00`–`24:00` 明确表达；
- 开始与结束相等属于非法配置；
- 整组规则不得覆盖一周中的每一分钟。

每个目标允许 1–128 条规则。每条规则的日期集合不得为空，并可包含可选说明。必须存在最多七天内可到达的非免拉取边界，保证 `no_fetch_until` 和 `next_run_at` 可计算。

动态 schedule 只计算拉取间隔；免拉取规则拥有更高优先级。免拉取结束后的第一次自动运行立即到期，之后恢复动态 schedule 或固定 fallback 间隔。

## 4. 数据与 API

### 4.1 数据库迁移

SQLite 与 PostgreSQL 同步增加迁移：

- `watch_targets.no_fetch_periods_json`：可空的版本化 JSON 配置；
- 用于区分待领取手动请求和当前租约触发来源的持久化字段；
- `crawl_runs.trigger_kind`：`unknown | scheduled | manual`。

迁移前的运行记录统一回填为 `unknown`，不能假定为自动运行。新代码创建运行记录时必须显式写入 `scheduled` 或 `manual`。

待领取的机器人手动请求必须持久化，worker 领取时原子地转移为当前租约的触发来源并清除待领取标记。该状态不能只保存在进程内存中，否则重启会丢失“手动运行可绕过免拉取”的语义。

### 4.2 写入契约

创建 TID/UID 目标接受可选的顶层字段：

```json
{
  "no_fetch_periods": [
    {
      "days": ["weekdays"],
      "start_time": "00:00",
      "end_time": "08:00",
      "description": "夜间"
    }
  ]
}
```

PATCH 使用三态替换语义：

- 字段缺失：不修改；
- `no_fetch_periods: null`：清空配置；
- 非空数组：完整替换；
- 空数组：`400 invalid_request`。

规则校验失败、开始结束相等或整周完全覆盖均返回 `400 invalid_request`。现有客户端不传该字段时行为保持不变。

### 4.3 读取契约

`WatchResponse` 增加：

- `no_fetch_periods`：保存的规则或 `null`；
- `no_fetch_active`：响应生成时是否命中；
- `no_fetch_until`：连续免拉取区间结束的完整 ISO 时间，未命中时为 `null`；
- `scheduler_timezone_offset`：解释规则所用的服务时区偏移。

`GET /api/v1/watches/{id}/runs` 的每条记录增加 `trigger_kind`。免拉取跳过继续通过现有 `status = skipped` 表达，不新增 crawl 或 watch 状态枚举。

## 5. 运行协调层

新增统一运行协调职责，供 worker、同步管理 API 和机器人排队入口共用：

1. 校验目标是否允许指定来源的运行；
2. 领取租约并固化 `scheduled` 或 `manual` 来源；
3. 创建运行记录并关闭可恢复的遗留运行；
4. 对自动运行求值免拉取状态；
5. 命中时完成跳过事务，否则把已经创建的 `run_id` 和配置快照交给 TID/UID collector；
6. 统一完成租约清理、下次调度和指标分类。

collector 不再各自创建运行记录，但继续负责采集、解析、内容事务、游标推进及采集错误分类。该边界保证两个 collector 不会重复实现免拉取逻辑。

免拉取求值应提供一个纯函数接口，同时返回“当前是否命中”和“连续区间结束时间”。它必须正确处理固定时区、跨午夜、周循环、重叠与相邻规则，并能在校验已排除整周覆盖的前提下终止。

## 6. 管理台

监控目标创建和编辑表单增加独立的“免拉取时段”编辑器：

- 日期多选；
- 开始与结束时间；
- “全天”开关，生成 `00:00`–`24:00`；
- 可选说明；
- 添加、删除和排序规则；
- 明确显示服务时区，例如 `UTC+08:00`。

监控列表在命中时显示“免拉取至 …”，但保留原 `active` 状态。运行详情将 `no_fetch_period` 显示为“免拉取时段跳过”，并展示自动、手动或未知触发来源，不把跳过渲染成失败。

页面使用服务端返回的派生字段解释规则，不在浏览器重复实现跨午夜和规则合并算法。规则边界按服务时区显示，运行记录时间戳保留完整 ISO 信息。

## 7. 指标与日志

新增 `crawl_runs_skipped_no_fetch_total`。免拉取跳过只增加该指标，不增加抓取成功或抓取失败计数。

结构化日志至少包含 `crawl_run_id`、`watch_id`、`trigger_kind`、`no_fetch_until`，并保持现有敏感信息约束。正常免拉取跳过使用信息级或调试级日志，不触发错误告警。

## 8. 实施顺序

1. 为免拉取规则、校验、当前状态和连续结束边界编写纯函数测试；覆盖时区、边界、跨午夜、重叠、相邻、全天和整周拒绝。
2. 增加 SQLite/PostgreSQL 迁移以及 repository 映射，验证历史 `trigger_kind = unknown`。
3. 扩展创建、更新、查询和 runs API；补充三态 PATCH 与错误契约测试。
4. 提取统一运行协调层，让两个 collector 接收已创建的 `run_id` 和触发来源。
5. 接入 worker、同步 `/run` 和机器人排队路径；覆盖手动绕过、暂停拒绝、重复请求和重启后来源保留。
6. 实现单次免拉取跳过事务、下次边界调度和手动运行后的审计机会保留。
7. 增加管理台编辑器、派生状态和运行详情展示。
8. 接入指标与结构化日志，更新 README/API/运维文档。
9. 在 SQLite 与 PostgreSQL 分别运行迁移和集成测试，并执行 `cargo test --all-targets`、严格 Clippy 与 release build。

## 9. 验收场景

- 60 秒间隔、00:00–08:00 免拉取只产生一条 0 请求跳过记录，08:00 自动恢复。
- 重叠和相邻规则只产生一个连续区间及一条跳过记录。
- 跨午夜规则在次日凌晨仍按开始日归属。
- 基线尚未完成时命中免拉取，不推进基线；结束后正常初始化。
- 免拉取期间的手动运行成功采集，随后仍能保证本区间存在且仅存在一条自动跳过记录。
- 暂停、鉴权暂停、已删除、正在运行和已排队目标拒绝不合法的手动请求。
- 普通配置更新不使正在运行的记录失败，新配置在下一轮生效。
- 服务停机跨过完整免拉取区间后不补造记录。
- 免拉取结束后累积内容照常保存、产生事件并进入通知 outbox。
- 历史运行显示 `unknown`，新自动和手动运行分别显示正确来源。
