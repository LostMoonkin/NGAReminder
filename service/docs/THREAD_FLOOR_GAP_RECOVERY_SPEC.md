# TID 楼层缺口补偿

## Goal

TID 增量采集当前只保存高水位之后可见的楼层。某个楼层因审核暂时不可见时，后续可见楼层会推动高水位越过它；该楼层恢复后因不再高于高水位而被永久遗漏。

本 Feature 在增量采集发现 `floor_number` 断层时持久化楼层缺口，并在首次发现后的 120 分钟内退避重试。恢复的楼层应像实时发现的新内容一样保存、匹配并通知，同时不重复处理已保存内容。

## Behavior

- 每次成功的非基线 TID 增量采集，以运行开始时的 `last_floor` 和本轮实际看到的最大普通楼层号确定新增楼层范围。
- 新增范围中未出现在本轮成功响应里的 `floor_number` 视为楼层缺口。楼中楼评论不参与断层计算。
- 新发现的楼层缺口必须持久化为 `pending`，并与本轮帖子写入和游标推进原子提交。
- 同一个监控目标下的同一楼层只能存在一条缺口记录；后续再次观察到相同断层不得重置首次发现时间或延长补偿期限。
- 缺口首次发现后，系统在第 5、15、35、65、95 和 120 分钟附近安排补偿尝试。调度延迟允许受 worker 轮询和请求节流影响，但不得主动安排到 120 分钟之后。
- 存在到期缺口时，即使正常监控间隔尚未到期，也应使该 TID 监控进入可运行状态；同一轮涉及的重复页面不得重复请求。
- 补偿抓取发现目标 `floor_number` 后，保存该普通楼层以及响应中按现有规则随其处理的楼中楼，并将缺口标记为 `resolved`。
- 恢复楼层即使不大于当前 `last_floor`，只要命中已记录的缺口，也必须绕过普通增量楼层过滤。
- 恢复楼层按现有实时事件、监控匹配和通知 outbox 语义处理；重复抓取不得产生重复帖子、事件、监控匹配或渠道投递。
- 任意正常 TID 抓取如果看到已记录的缺口楼层，也应完成相同的恢复处理，不必等待专门的补偿时间。
- 到首次发现满 120 分钟时执行最后一次允许的补偿尝试；楼层仍不可见则将缺口标记为 `expired`，此后停止主动补偿。
- `expired` 缺口以后被正常抓取碰到时，仍可保存对应楼层并转为 `resolved`。
- 补偿页面暂时请求失败不得导致已经成功取得的正常增量内容被丢弃，也不得删除缺口；缺口保留到后续允许的尝试。
- 自动补偿属于自动运行，遵守监控目标的免拉取时段。手动运行沿用现有规则，可以绕过免拉取时段并顺带处理到期缺口。
- 暂停监控不执行补偿且不暂停 120 分钟期限。重置监控时清除该监控尚存的缺口；删除监控时一并删除其缺口记录。

## Constraints

- 本 Feature 只适用于 Rust 服务的 TID 采集，不改变 UID 采集语义。
- 楼层缺口必须根据普通帖的 `floor_number` 断层判断，不使用 `vrows` 推测具体缺失楼层。
- 首次全量基线和 `incremental` 基线均不得创建楼层缺口或发送缺口通知；本 Feature 不改变现有初始化模式。
- 缺口及其状态、首次发现时间、重试进度、下次尝试时间和 120 分钟期限必须持久化，服务重启后仍能继续正确处理。
- SQLite 和 PostgreSQL 必须使用同号迁移，并保持可观察约束和行为一致。
- 游标推进、缺口创建、帖子持久化、事件匹配、outbox 入队和运行完成必须保持现有事务一致性要求。
- 所有 NGA 请求继续经过现有账号级节流、重试、租约和统一运行协调逻辑。
- 恢复内容继续使用现有帖子自然键、`post_events`、`post_event_watch_matches` 和通知 outbox 去重约束。
- 本 Feature 不新增用户可配置项；120 分钟期限和退避节奏是服务端固定行为。

## Out of Scope

- 扫描或补建启用本 Feature 之前已经越过的历史楼层缺口。
- 在基线期间枚举历史删帖、无权访问楼层或其他既有断层。
- 对 120 分钟后仍不可见的楼层继续主动重试。
- 监控后来追加到旧父帖的楼中楼评论。
- 新增缺口管理 API、管理台配置项或人工编辑缺口状态的功能。
- 将相同行为同步到 `extension-standalone`。

## Acceptance Criteria

- 已有 `last_floor = 100` 时，本轮成功响应看到 `#102` 而未看到 `#101`：本轮提交后游标为 102，`#102` 已正常处理，`#101` 存在唯一的 `pending` 缺口记录。
- 上述事务在提交前失败时，游标、帖子和新缺口均不产生部分提交。
- `#101` 在补偿期限内恢复时，即使当前游标已经大于 101，也会被保存并生成一次符合监控过滤条件的事件、匹配和 outbox；缺口变为 `resolved`。
- 同一恢复响应被重复处理，或之后的正常运行再次看到 `#101`，帖子、事件、匹配和渠道通知均不重复。
- 连续缺失多个普通楼层时，每个缺失 `floor_number` 都独立留下缺口，并可分别恢复或过期。
- 缺口一直不可见时，系统按约定退避且不把首次发现时间向后延长；120 分钟的最后尝试后状态变为 `expired`，不再触发主动补偿。
- 补偿页面请求失败而正常增量页面成功时，正常新增内容和游标可以提交，缺口仍保留并可继续重试。
- 全量基线、`incremental` 基线和无新增楼层的正常运行不会创建历史缺口或历史通知。
- 自动运行命中免拉取时段时不发生缺口补偿 NGA 请求；免拉取跳过仍保持现有零请求、零游标推进语义。
- 重启服务不会丢失 `pending` 缺口及其原有首次发现时间、期限和重试进度；重置或删除监控后旧缺口不再触发补偿。
- SQLite 和 PostgreSQL 的迁移均可应用，相关本地数据库/fixture 测试覆盖断层发现、恢复、幂等、过期和事务回滚。
