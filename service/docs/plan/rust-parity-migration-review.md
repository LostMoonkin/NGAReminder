本轮特别补齐了 `requiredSchema` 中的主题完整元数据、帖子页码、资源原文件名、系统告警及其投递、远端分页快照和缺口提示页；缺少这些列会明确失败，不能用零值悄悄代替。验证器除行数和关联外，还对照源快照检查主题字段、帖子页码和完整 raw。

## 已有 Go 库升级

- 表和投递唯一索引在一个 SQLite 事务中升级，不删除帖子、事件或投递。连续打开升级后的库仍保持相同业务数据。
- 主题标题优先恢复当前 TID watch 的标题，再使用已保存主楼/回复 subject；已知作者和远端快照同时保留。只有帖子、没有主楼的旧 UID 内容也参与回填。
- 旧 Go 未保存的真实页码、raw、版面和完整覆盖信息无法还原，保留未知，不通过重新全量抓取补齐。
- 仅对最近一次旧运行明确记录 code14 对应“主题不存在，已停止自动采集”的 UID 修复误停状态；不推进水位，不改变手动暂停。
- 旧 Go 已经删除的 watch 若未保留来源类型，无法从现有数据可靠恢复其事件类型；事件、备注、正文及投递仍保留。Rust PG 迁移有完整 watch 快照，包含已删除来源，不受此限制。

## 实际验证与边界

- 主 Go 模块：`CGO_ENABLED=0 go build ./...`、`go vet ./...`、`go test ./...`。
- 独立迁移模块另行 build、vet、test；主模块的 `./...` 不覆盖这个嵌套模块。
- 使用独立 PostgreSQL 17 临时容器及归档 0001～0007 schema 构造假数据，真实执行导出 → SQLite 转换 → 校验 → Go 管理页/解密/ZIP/增量读取。包含源库导出前后不变、同快照离线重放一致、截断快照/错误密钥/悬空评论/未来 schema 拒绝等检查。
- 旧 Go 升级 fixture 覆盖正文、事件来源、内容/告警投递共存、远端快照、C02 误停恢复及重复打开；本次未改动真实业务库。
- 文档相对链接与 `git diff --check` 单独检查。

审查未发现尚未处理的、会阻塞本次范围内迁移的数据遗漏。**正式切换仍需使用实际旧库副本和原 assets 挂载执行 [迁移核验流程](migration-runbook.md)**；本地假数据通过不代表生产数据已完成迁移。旧部署的下载上限和 raw 开关不在 PG 中，需从旧配置分别设置 `NGA_REMINDER_MAX_DOWNLOAD_BYTES`、`NGA_REMINDER_STORE_RAW_PAYLOAD`。
