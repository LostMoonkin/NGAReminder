# 阶段 04：通知与收件箱

后续行为补充以 [Spec12：Rust 行为对齐与迁移补全](12-rust-parity-fixes.md) 为准。

## 目标

把监控发现的新内容发送到现有 Bark 和飞书渠道，并在管理页保留可查看的内容与投递结果。
用户能够判断是否匹配、是否已发送以及失败原因。

## 行为

- 管理页可配置、测试、启停和删除 Bark/飞书通知目标；密钥与完整收件地址不在列表回显。
- Bark 支持设备 key、自定义服务地址和分组；飞书使用自建应用机器人，支持配置应用凭据与接收目标。
- 飞书应用凭据统一配置，通知目标只选择接收者；阶段 05 的 Bot 复用同一个应用连接。
- 飞书应用保存后明确显示已配置状态并回显 App ID，表单默认禁用编辑；点击“修改”后可编辑，保存或取消后恢复锁定。App Secret 始终不回显，修改时留空保留；未配置时直接填写并保存。
- 每个 watch 选择通知渠道；TID 可设置作者 UID 白名单，空白名单表示全部作者，UID 只匹配目标用户。
- 不命中作者条件的内容仍保存，但不创建新内容事件或通知；基线初始化保持静默。阶段 08 的历史回填沿用静默规则。
- 命中的增量内容进入收件箱，可查看正文摘要、来源监控、来源链接并标记已读/未读。
- 同一内容被多个监控发现时，收件箱不重复展示，同一渠道也不重复入队；不同渠道分别投递。
- 通知包含主题、作者、正文与可定位回复的 NGA 链接；飞书使用下述 Rust 卡片规则，Bark 继续使用纯文本摘要。
- 飞书通知沿用原卡片样式：蓝色标题栏、`lark_md` 正文、作者/楼层与正文之间空一行，以及蓝色“查看帖子”按钮。原帖地址只作为按钮跳转目标，不再额外追加到正文末尾；正文原有链接和图片失败时的源链接仍保留。
- 飞书标题使用原始主题标题；匹配 UID 监控时使用“用户监控：昵称”，作者为空时使用 UID。标题按 Unicode 字符截取前 80 字，超长追加 `…`。
- 飞书正文从“作者 · #楼层”、空行与原始 NGA 正文生成，独立复刻 Rust `render_compact_markdown`，不经过纯文本摘要或 ngapost2md。Reply 的 `[pid]`、`[uid]` 只保留内部文字；保留粗体、斜体、下划线、删除线、引用、折叠引用、换行和链接；去掉代码围栏及纯装饰代码，保留有内容的代码、论坛表情和未知标记。空白行压缩与末尾换行沿用 Rust。
- 正文在渲染后按 Unicode 字符限制为 2000 字（含作者、楼层和截断提示）；超长时保留前缀并追加 `…`、空行及 `内容较长，点击“查看帖子”查看完整内容。`。
- 按正文中 `[img]…[/img]` 的出现顺序提取图片并移出文本，不使用帖子附件列表替代，也不去重。仅前三个图片位置尝试上传；成功图片依次排在正文后，替代文本为“NGA 帖子图片”。失败和超出三张的所有图片保留在独立 `lark_md` 区块，按回退顺序显示 `[图片 1](URL) · [图片 2](URL)`，最后放原帖按钮。
- 飞书图片沿用三个 HTTPS 域名白名单和 10 MiB 上限；下载超时 30 秒，仅跟随白名单内的 HTTPS 重定向，最多四次。要求非空内容及 `image/*` 响应类型；下载或上传失败不阻止文本投递。同一进程按应用与图片地址缓存成功上传的 image key，重复图片复用；普通资源下载仍遵守阶段 07 的独立规则。
- 保存事件和待发送记录后异步投递，发送失败不回滚已采集内容或游标。
- 页面显示待发送、成功或失败及最近错误；临时发送失败最多尝试五次（含首次），之后等待用户手动重试。
- 关闭渠道暂停新增投递和已有记录的重试，不关闭 Bot；被 watch 引用的渠道删除前提示解除引用，保留可读的历史结果。
- 服务重启后仍可看到投递结果和未完成记录；不承诺“第三方已收到但本地未记成功”场景绝不重复发送。

## 约束

- 依赖 [阶段 03](03-user-monitoring-and-scheduling.md)，使用 [AGENTS.md](../../AGENTS.md) 规定的事务、日志和脱敏方式。
- Bark 与飞书调用放在 infrastructure；通知匹配由 service 决定，不另建可插拔通知平台。
- 飞书使用 [官方 Go SDK](https://github.com/larksuite/oapi-sdk-go)，当前只配置一个应用，可有多个接收目标。
- 投递状态保存在 SQLite，发送由当前进程执行；重试仅针对通知这一具体功能。

## 非目标

- Telegram、QQ、自定义 webhook 和通用 Provider 框架。
- 外部消息队列、通知审计平台和严格 exactly-once 保证。
- Bot 指令与 Cookie 续期交互。

## 验收标准

- [x] 管理页可以配置和测试 Bark/飞书；关闭渠道后不再新增投递或自动重试。
- [x] 飞书应用保存后回显 App ID 并锁定；修改、取消、保存和刷新后的状态正确，App Secret 不回显且留空保留。
- [x] 基线和白名单外内容不进入收件箱或通知，普通匹配增量正常进入。
- [x] 同一帖子被 TID/UID 监控同时命中时，收件箱一条、每个渠道一条待发送记录。
- [x] 临时失败可有限重试，达到上限后页面可见错误并可手动重试；日志包含渠道 ID、发送结果和错误栈。
- [x] 飞书图片下载/上传失败仍可发送文本与源链接，通知链接可定位到回复。
- [x] Reply、格式、代码、图片提取和截断与归档 Rust 执行结果一致；实际投递卡片验证原始标题、UID 名称回退、长正文、图片区块顺序、超量链接及应用间缓存隔离。
- [x] 收件箱已读状态和发送结果在重启后保留，日志与 API 不暴露密钥或收件地址。

## 实现与自测

已完成（2026-09-17）。管理页及 API 见 [服务端文档](../README.md#通知与收件箱阶段-04)。

使用 Gin、真实 SQLite、NGA/Bark/飞书 HTTP fixture 验证基线静默、作者过滤、跨监控去重、渠道关闭、删除引用检查、五次重试和手动恢复、图片下载/上传失败回退、已读与投递重启持久化及脱敏。`CGO_ENABLED=0` 下 build、vet、全套测试通过，新增通知测试通过；文档链接与 `git diff --check` 通过。没有向真实 Bark/飞书发送消息。

飞书应用编辑交互另用临时 SQLite 和 Chromium 验证首次配置、App ID 回显、默认锁定、修改/取消/保存、刷新与窄屏布局；API/页面/日志不暴露 Secret。接口测试验证修改 App ID 时 Secret 留空保留，以及 App ID 重启后仍可回显。

飞书卡片样式回归：Go 卡片生成遗漏蓝色标题栏和 primary 按钮，共用正文格式又重复追加了原帖地址。使用 [真实投递链测试](../../internal/handler/feishu_card_test.go) 复现后修复，验证 TID/UID 通知的标题栏、正文间距、按钮样式和链接位置，发送请求由本地 HTTP fixture 接收。Bark 保留原有正文和跳转地址。修复后 `CGO_ENABLED=0` 下 build、vet、全套测试及 `git diff --check` 通过。

2026-09-20 补齐正文和图片规则：原 Go 投递先调用纯文本摘要，导致 Reply 泄漏 `[pid]`/`[uid]` 且丢失粗体。以 [Rust markup](../../../archive/rust-service/service/src/markup.rs) 和 [Rust sender](../../../archive/rust-service/service/src/notification/sender.rs) 为基准，新增独立 [飞书转换器](../../internal/content/feishu.go)。[25 组预期样例](../../internal/content/testdata/feishu_rust.json) 由 Rust 原函数实际执行生成，覆盖嵌套格式、Reply、未知/不完整标记、代码、表情、图片和 Unicode 截断；[图片下载测试](../../internal/infrastructure/feishu_images_test.go) 验证类型、大小、空内容与重定向，真实投递链测试验证最终 SDK 卡片和缓存。`CGO_ENABLED=0` 下 build、vet、全套测试通过，格式、文档相对链接和 `git diff --check` 通过。全部使用本地 fixture，不向真实飞书发送消息。
