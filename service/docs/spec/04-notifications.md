# 阶段 04：通知与收件箱

## 目标

把监控发现的新内容发送到现有 Bark 和飞书渠道，并在管理页保留可查看的内容与投递结果。
用户能够判断是否匹配、是否已发送以及失败原因。

## 行为

- 管理页可配置、测试、启停和删除 Bark/飞书通知目标；密钥与完整收件地址不在列表回显。
- Bark 支持设备 key、自定义服务地址和分组；飞书使用自建应用机器人，支持配置应用凭据与接收目标。
- 飞书应用凭据统一配置，通知目标只选择接收者；阶段 05 的 Bot 复用同一个应用连接。
- 每个 watch 选择通知渠道；TID 可设置作者 UID 白名单，空白名单表示全部作者，UID 只匹配目标用户。
- 不命中作者条件的内容仍保存，但不创建新内容事件或通知；基线初始化保持静默。阶段 08 的历史回填沿用静默规则。
- 命中的增量内容进入收件箱，可查看正文摘要、来源监控、来源链接并标记已读/未读。
- 同一内容被多个监控发现时，收件箱不重复展示，同一渠道也不重复入队；不同渠道分别投递。
- 通知包含主题、作者、正文摘要与可定位回复的 NGA 链接；飞书最多附带三张可用图片，图片失败时保留链接并继续发送文本。
- 保存事件和待发送记录后异步投递，发送失败不回滚已采集内容或游标。
- 页面显示待发送、成功或失败及最近错误；临时发送失败最多尝试五次（含首次），之后等待用户手动重试。
- 关闭渠道暂停新增投递和已有记录的重试，不关闭 Bot；被 watch 引用的渠道删除前提示解除引用，保留可读的历史结果。
- 服务重启后仍可看到投递结果和未完成记录；不承诺“第三方已收到但本地未记成功”场景绝不重复发送。

## 约束

- 依赖 [阶段 03](03-user-monitoring-and-scheduling.md)，使用 [AGENTS.md](../../AGENTS.md) 规定的事务、日志和脱敏方式。
- Bark 与飞书调用放在 infrastructure；通知匹配由 service 决定，不另建可插拔通知平台。
- 飞书使用 [官方 Go SDK](https://github.com/larksuite/oapi-sdk-go)，当前只配置一个应用，可有多个接收目标。
- 投递状态保存在 SQLite，发送由当前进程执行；重试仅针对通知这一具体功能。

## 非目标

- Telegram、QQ、自定义 webhook 和通用 Provider 框架。
- 外部消息队列、通知审计平台和严格 exactly-once 保证。
- Bot 指令与 Cookie 续期交互。

## 验收标准

- [x] 管理页可以配置和测试 Bark/飞书；关闭渠道后不再新增投递或自动重试。
- [x] 基线和白名单外内容不进入收件箱或通知，普通匹配增量正常进入。
- [x] 同一帖子被 TID/UID 监控同时命中时，收件箱一条、每个渠道一条待发送记录。
- [x] 临时失败可有限重试，达到上限后页面可见错误并可手动重试；日志包含渠道 ID、发送结果和错误栈。
- [x] 飞书图片下载/上传失败仍可发送文本与源链接，通知链接可定位到回复。
- [x] 收件箱已读状态和发送结果在重启后保留，日志与 API 不暴露密钥或收件地址。
